# Часть 0. Общее — спросят на любой лабе

## Жизнь кадра

```
compute (частицы)  →  shadow pass  →  geometry pass  →  light pass  →  post
   ParticleSystem      4 каскада       3 RT + depth     HDR-буфер     back buffer
```

`Framework::Draw()` в конце делает `FlushCommandQueue()` — полная синхронизация
CPU/GPU каждый кадр. Это упрощает всё (буферы в UPLOAD можно перезаписывать без
гонок), но убивает параллелизм: CPU простаивает, пока GPU не закончит. Правильно —
frame resources на 2–3 кадра (лекция 01, слайд 44).

## Классы

| Класс | Ответственность |
|---|---|
| `Framework` | окно, устройство, очередь, swap chain, depth-буфер, камера, ввод |
| `RenderingSystem` | сцена, G-Buffer, root signatures, PSO, свет, все проходы |
| `GBuffer` | 3 RT + SRV на глубину, кучи RTV/SRV, барьеры |
| `ShadowMap` | массив каскадов, DSV на срез, математика каскадов |
| `ObjectField` | 4096 коробок, окто-дерево, отсечение, инстансинг |
| `ParticleSystem` | буферы частиц, compute, indirect-отрисовка |
| `PostProcess` | HDR-буфер, bloom, тональное отображение |

## Три вещи, которые надо уметь объяснить про D3D12

**Кучи дескрипторов.** Одновременно можно привязать только одну кучу типа
`CBV_SRV_UAV`. Поэтому SRV карты теней лежат не в своей куче, а в куче G-Buffer,
в слоте `t4`. Размер дескриптора берётся из `GetDescriptorHandleIncrementSize` —
он зависит от драйвера, хардкодить нельзя.

**Барьеры.** Ресурс не может одновременно быть render target и текстурой для
чтения. Переходы явные: `RENDER_TARGET → PIXEL_SHADER_RESOURCE` после
геометрического прохода, обратно перед следующим кадром. `GBuffer` и `PostProcess`
отслеживают состояние сами, чтобы не выдать барьер с `StateBefore == StateAfter` —
это ошибка уровня отладки.

**Root signature.** Root CBV дешевле таблицы (адрес кладётся прямо в командный
список, без похода в кучу), но root-параметров всего 64 DWORD. Текстуры идут
таблицей, константы — прямыми CBV. У поля объектов своя маленькая сигнатура
с флагами `DENY_*_SHADER_ROOT_ACCESS` — прямая рекомендация слайда 34 лекции 05.

# Лаба 1 — Текстурирование и загрузка моделей

**Задание (лекция 02, слайд 44):** добавить загрузку текстур; отрисовку obj-моделей

> переехало в `GeometryPass.hlsl`. `Phong.hlsl` лежит в проекте как справка и

## Решение

- **Текстуры** — только DDS, через `DirectX::CreateDDSTextureFromFile12` (слайд 17).
- **Кэш** по полному пути файла: одна DDS в Sponza указана у нескольких материалов.
  В кэш кладётся и `nullptr` — битый файл не открывается повторно.
- **Белая текстура 1×1** подставляется вместо отсутствующей, чтобы в шейдере
  не было ветвления «есть текстура / нет». Тот же приём — слайд 37 лекции 09.
- **SRV-куча материалов**: по 4 дескриптора на материал = `t0` diffuse, `t1` альфа,
  `t2` нормали, `t3` высоты. Смещение: `materialSlot * 4 * descSize`.
- **Сэмплер статический** (слайд 41), `ANISOTROPIC`, `MaxAnisotropy = 8`, `WRAP` по
  всем осям, `s0`, видимость `ALL` (domain shader тоже сэмплирует).
- **OBJ** — tinyobjloader с `triangulate = true`. V переворачивается: `1 - v`.
- **Один подмеш = один материал**, вершины лежат непрерывным диапазоном.
- **Нормализация**: `Translate(-center) * Scale(2/maxDim)`, вершины в буфере
  не переписываются.

## Вопросы

**Почему DDS, а не PNG?** DDS хранит готовую цепочку мипов, блочно сжатые форматы
(BC1–BC7), которые GPU распаковывает аппаратно, и пиксельные форматы прямо
из `DXGI_FORMAT` (слайды 12–14). PNG пришлось бы декодировать на CPU и грузить
несжатым: 1024×1024 в BC3 — 1 МБ, в `R8G8B8A8` — 4 МБ.

**Почему нельзя освободить upload-буфер сразу?** `ExecuteCommandLists` только ставит
работу в очередь. Пока GPU не выполнил копирование, источник должен быть жив.

**Почему статический сэмплер?** Слайд 41: сэмплеров в приложении единицы, для этого
есть `D3D12_STATIC_SAMPLER_DESC` — не нужна отдельная куча и лишний root-параметр.

**Что будет при `ADDRESS_MODE_CLAMP`?** Тайлинг сломается: вместо повторов текстура
растянется, всё за [0,1] станет размазанным краем.

**Откуда мипы?** Из файла, `MipLevels` копируется из `GetDesc()`. В рантайме
не генерируются.

**Почему нет индексного буфера?** В OBJ позиция, нормаль и UV индексируются
независимо — нужен словарь уникальных троек. Не сделано. Цена: буфер весит
`число_вершин × 48` байт, каждая общая вершина лежит столько раз, сколько граней
её используют. С индексацией было бы примерно в 2–3 раза меньше.

**Почему VB в UPLOAD-куче?** Модель статична, не хотелось второго копирования.
Минус честный: буфер в системной памяти, GPU читает через PCIe, а не из VRAM.

**Показать:** `T` — анимация UV, `]`/`[` — тайлинг ×2 / ÷2, `0` — сброс, `F1` — альбедо.

**Не закрыто:** не-DDS форматы (нет WIC/stb), генерация мипов в рантайме,
индексный буфер, кубические и объёмные текстуры.

# Лаба 2 — Отложенный рендеринг

**Задание (лекция 03, слайд 38):** класс `RenderingSystem`; класс `GBuffer`;
deferred rendering; источники точечный / directional / spot; Sponza + несколько
источников по сцене.

## Решение

Раскладка G-Buffer (после лабы 8):

| Слот | Что | Формат |
|---|---|---|
| t0 | альбедо | `R8G8B8A8_UNORM_SRGB` |
| t1 | мировая нормаль | `R16G16B16A16_FLOAT` |
| t2 | metallic / roughness / AO | `R8G8B8A8_UNORM` |
| t3 | глубина | `R24_UNORM_X8_TYPELESS` (SRV на depth-буфер) |

- **Мировые координаты не хранятся** — восстанавливаются из глубины и
  `InvViewProj` (слайд 17). Экономия одного таргета `R32G32B32A32_FLOAT` =
  16 байт на пиксель.
- Чтобы один буфер был и DSV, и SRV, он создаётся как `R24G8_TYPELESS`.
- `OMSetRenderTargets(3, &rtv, TRUE, &dsv)` — дескрипторы RTV лежат подряд,
  поэтому один handle с флагом `RTsSingleHandleToDescriptorRange = TRUE`.
- **Световой проход**: на каждый источник — один полноэкранный треугольник
  из `SV_VertexID` (слайд 23), аддитивный блендинг `ONE + ONE` (слайды 13, 36),
  запись глубины выключена, DSV не привязан вообще.
- G-Buffer читается через `Texture2D.Load(int3)` (слайд 20) — без сэмплера
  и без интерполированных UV.
- **Ambient — отдельный «тип источника»** (слайд 13), иначе он прибавится
  на каждый свет и сцена пересветится.

## Ключевой код

```hlsl
// Полноэкранный треугольник, без VB и input layout (слайд 23)
float2 uv = float2((id << 1) & 2, id & 2);
return float4(uv * float2(2.0f, -2.0f) + float2(-1.0f, 1.0f), 0.0f, 1.0f);
```

```hlsl
float3 ReconstructWorldPos(float2 pixelXY, float depth)
{
    float2 ndc = pixelXY * gInvScreen * float2(2.0f, -2.0f) + float2(-1.0f, 1.0f);
    float4 world = mul(float4(ndc, depth, 1.0f), gInvViewProj);
    return world.xyz / world.w;
}
```

Свет: 1 ambient + 1 directional + 5 точечных вдоль атриума + 2 прожектора.
Затухание точечного: `(1 - d/Range)²`, `discard` при `d > Range`. Прожектор —
то же × конус по `cosOuter`/`cosInner`.

## Вопросы

**Зачем вообще deferred?** В forward стоимость — `объекты × источники`: каждый
пиксель считается заново для каждого света, включая те, что потом перекроются.
В deferred — `объекты + источники`: геометрия пишется один раз, свет считается
по пикселям экрана (слайды 5, 8).

**Минусы deferred (слайд 14)?** Прозрачность не работает (в G-Buffer помещается
только ближайшая поверхность) — нужен отдельный forward-проход. MSAA сложнее:
надо хранить и разрешать все сэмплы G-Buffer. Память: у нас 4+8+4 = 16 байт
на пиксель только на цветные таргеты, в 1920×1080 это ~33 МБ.

**Почему треугольник, а не квад?** Квад — два треугольника с диагональю: пиксели
вдоль шва растеризуются дважды (квады 2×2 на границе). Один треугольник, покрывающий
весь NDC, шва не имеет (слайды 22–23).

**Почему не световые объёмы (сферы/конусы)?** Слайд 21 предлагает рисовать геометрию
источника и отсекать растеризатором + depth bound test. У нас вместо этого
полноэкранный треугольник и `discard` по расстоянию — проще, но пиксельный шейдер
запускается на весь экран для каждого источника. При десятках источников это
и есть проблема со слайда 25.

**Почему глубину не хранить отдельным таргетом?** Она уже есть — depth-буфер.
Его достаточно объявить `TYPELESS` и создать на него SRV.

**Почему `Load`, а не `Sample`?** `SV_POSITION` в пиксельном шейдере — уже
координаты пикселя. Фильтрация G-Buffer бессмысленна и вредна: интерполировать
нормали и глубину соседних поверхностей нельзя.

**Показать:** `F1`–`F5` — каналы G-Buffer, `+`/`-` — яркость всех источников.

**Не закрыто:** transparent stage (слайд 12), световые объёмы с depth bound test
(слайды 21, 24), Forward+ / tiled deferred (слайды 26–31).

# Лаба 3 — Тесселяция

**Задание (лекция 04, слайд 75):** найти модели с displacement и normal текстурами;
реализовать тесселяцию со сдвигом по displacement-текстуре; использовать карту
нормалей; менять уровень тесселяции в зависимости от удалённости от камеры.

## Главная находка

В этой сборке Sponza файлы `*_bump.dds` — **не карты нормалей, а полутоновые карты
высот**: R ≈ G ≈ B, длина вектора `2c − 1` = 0.24…0.71 вместо 1.0. Проверено
декодированием DXT5.

Отсюда: `*_bump.dds` идут как displacement напрямую, а карты нормалей сгенерированы
из тех же карт высот скриптом `tools/make_normal_maps.py` (градиент по Собелю,
упаковка по слайду 4). Слайд 38 именно это и требует — карта нормалей должна быть
**согласована** с картой смещения, иначе освещение разойдётся с геометрией.

## Решение

```
обычный      VS      →                     PS
тесселяция   VS_Tess → HS → [тесселятор] → DS → PS
```

Оба конвейера в одном `GeometryPass.hlsl` и делят пиксельный шейдер — так раскладка
cbuffer'ов гарантированно совпадает.

| Стадия | Что делает |
|---|---|
| `VS_Tess` | в мировое пространство, **без** проекции |
| `ConstantsHS` | коэффициенты рёбер по расстоянию до камеры |
| `HS` | pass-through контрольных точек (слайд 38: драйвер оптимизирует этот шаблон) |
| `DS` | барицентрическая интерполяция, выборка высоты, сдвиг вдоль нормали, проекция |
| `PS` | общий: normal mapping + запись в G-Buffer |

Атрибуты: `[domain("tri")]`, `[partitioning("fractional_odd")]`,
`[outputtopology("triangle_cw")]`, `[outputcontrolpoints(3)]`, `[maxtessfactor(8.0)]`.

Вершина: `Color` (не использовался) заменён на `TangentU` (float4, `w` = хиральность).
**Stride остался 48 байт**, поменялся только семантик в input layout.

## Ключевой код

```hlsl
    return lerp(gTessFactorMax, gTessFactorMin, t);
```

## Вопросы

**Почему коэффициент ребра считается только по его двум концам?** Потому что два
соседних патча делят эти же две вершины, получают одинаковый коэффициент — и щели
вдоль шва не возникает. Если считать фактор от центра патча, шов немедленно
разъезжается. Это ключевой вопрос по теме.

**Почему `fractional_odd`, а не `integer`?** При целочисленном разбиении геометрия
скачком меняется при движении камеры — видно «дёрганье». Дробное разбиение вводит
новые вершины плавно.

**Зачем `2c − 1` при чтении карты нормалей?** Нормаль лежит в [−1,1], а текстура
хранит [0,1]: упаковка `(n+1)*0.5`, распаковка `n = 2c − 1` (слайд 4).

**Что такое `w` в касательной?** Хиральность базиса: знак `dot(cross(N,T), B)`.
Нужна, потому что при зеркальной развёртке UV бинормаль смотрит в другую сторону.
Хранить её дешевле, чем весь вектор B.

**Что тесселируется и почему не всё?** Материал с `map_bump` и без `map_d` — восемь
каменных материалов. Листва и цепи карту высот имеют, но это плоские билборды
с вырезанной альфой, смещать их бессмысленно.

**Почему касательная одна на грань?** Буфер невершинно-индексированный: усреднять
по вершинам негде. Ортогонализация делается в PS по Граму-Шмидту.

**Показать:** `G` — тесселяция вкл/выкл, `F` — каркас (видно, как растёт сетка при
приближении), `N` — карты нормалей, `,`/`.` — сила смещения,
`PageUp`/`PageDown` — максимальный фактор.

**Не закрыто:** швы на границе тесселируемого и нетесселируемого подмеша;
parallax mapping (слайды 12–19); поверхности Безье (39–44); отбраковка задних
патчей есть, но выключена — растеризатор работает в `CULL_NONE` ради односторонней
геометрии Sponza, и отбраковка срезала бы её же.

# Лаба 4 — Оптимизация (frustum culling)

**Задание (лекция 05, слайд 37):** раскидать по сцене несколько тысяч объектов;
реализовать frustum culling; вкл/выкл; реализовать окто-дерево; вкл/выкл для
отсечения с деревом.

## Решение

**Плоскости пирамиды — Gribb–Hartmann**, прямо из `ViewProj`, без обратных матриц.
Соглашение DirectXMath — вектор-строка (`clip = p · M`), поэтому `clip.x` собирается
из нулевого **столбца**:

```
левая   = столбец3 + столбец0        нижняя  = столбец3 + столбец1
правая  = столбец3 − столбец0        верхняя = столбец3 − столбец1
ближняя = столбец2  (в DX z из [0..w])   дальняя = столбец3 − столбец2
```

Матрица кладётся **без транспонирования** — в отличие от константных буферов.
Плоскости нормируются, иначе «расстояние» в произвольных единицах.

**Тест AABB** — проекция полуразмера на нормаль вместо перебора 8 вершин:

```
r = |e.x·n.x| + |e.y·n.y| + |e.z·n.z|
d = dot(n, center) + w

d + r < 0 → Outside;  d − r < 0 → Intersects;  иначе → Inside
```

**Окто-дерево**: корень — объединение всех коробок; узел делится на 8, пока в нём
> 8 объектов и глубина < 8; объект кладётся в **самый глубокий узел, полностью его
содержащий** — пересекающий границу остаётся в родителе.

Обход: `Outside` → выходим; `Inside` → собираем всё поддерево без тестов;
`Intersects` → проверяем объекты узла и спускаемся.

**Инстансинг**: 4096 коробок одним `DrawIndexedInstanced`. Второй вершинный поток
с `PER_INSTANCE_DATA` несёт центр, полуразмер и цвет — 48 байт. Буфер в UPLOAD,
замаплен на всё время жизни, каждый кадр перезаписывается только видимыми.

## Вопросы

**Зачем отдельное значение `Inside`, а не bool?** В этом весь смысл иерархии: узел
целиком внутри пирамиды означает, что всё его поддерево видимо, и тесты для него
не нужны. С bool пришлось бы тестировать каждый объект.

**Почему объект, пересекающий границу, остаётся в родителе?** Иначе пришлось бы
расширять границы узлов под выступающие объекты, и тест узла перестал бы быть
корректным для поддерева.

**Почему не видно разницы в FPS между режимами 2 и 3?** Правильное отсечение
визуально невидимо по определению — картинка обязана быть одинаковой. Смотреть надо
на счётчики в заголовке: **число нарисованных объектов совпадает** (обе реализации
корректны), а **число тестов AABB** у дерева в разы меньше. Клавиша `P` замораживает
пирамиду — тогда отсечённый объём становится видно.

**Почему нет гонки с GPU при перезаписи буфера экземпляров каждый кадр?**
`Framework::Draw()` делает `FlushCommandQueue()` в конце кадра. Правильно было бы
кольцо буферов по числу кадров в полёте.

**Грабли при построении дерева?** `m_nodes[index].children[i] = child;` пишется
после рекурсивного вызова и **через индекс, а не через сохранённую ссылку** —
вектор узлов мог перевыделиться внутри рекурсии.

**Показать:** `1` — отсечение выкл (точка отсчёта по FPS), `2` — перебор, `3` —
дерево, `O` — коробки узлов каркасом, `P` — заморозить пирамиду.

**Не закрыто:** occlusion culling (слайды 11–12), LOD (7), z-prepass (15–17),
многопоточное отсечение (21), bundles (25).

# Лаба 5 — Каскадные тени

**Задание (лекция 06, слайд 53):** добавить каскадные карты теней; использовать
нелинейное распределение каскадов; использовать PCF.

## Решение

**Хранилище** — одна `Texture2DArray` `R32_TYPELESS`, 2048×2048, 4 среза.
Запись: свой DSV на срез (`D32_FLOAT`, `FirstArraySlice = i`). Чтение: один SRV
на весь массив, лежит в SRV-куче G-Buffer в слоте `t4`.

**Нелинейное распределение** — practical split scheme:

```
логарифмическое  d_i = n · (f/n)^(i/N)
равномерное      d_i = n + (f − n)·(i/N)
итог             d_i = λ·log_i + (1 − λ)·uniform_i        λ = 0.75
```

Чисто логарифмическое идеально по плотности текселей, но первый каскад крошечный;
равномерное — грубое вблизи. Смесь и есть требуемая нелинейность.

**Матрицы света** (слайды 26–29): восемь углов под-фрустума в мир → **центр и радиус
описанной сферы** (не AABB: размер каскада тогда не зависит от поворота камеры,
и тени не «кипят») → радиус квантуется `ceil(r·16)/16` → `LookAtLH` из
`центр − dir·(r + backOff)` → `OrthographicOffCenterLH(-r, r, -r, r, 0, 2r+backOff)`
→ **привязка к сетке текселей**: начало каскада проецируется, переводится в тексели,
округляется, разница добавляется в строку сдвига проекции. Без этого края теней
мерцают при движении камеры.

**Проход теней**: viewport размером с карту (слайд 30), `OMSetRenderTargets(0, nullptr,
FALSE, &dsv)`, `pso.PS = { nullptr, 0 }` и `NumRenderTargets = 0` — пиксельного
шейдера нет вообще (слайд 14). Поле коробок рисуется **целиком**, а не отобранной
частью: объект вне пирамиды камеры вполне может отбрасывать тень внутрь неё.

Смещение — состоянием растеризатора (слайды 18–20):

```cpp
raster.DepthBias            = 1200;
raster.SlopeScaledDepthBias = 1.8f;
raster.DepthBiasClamp       = 0.01f;
```

**PCF** (слайды 39–40): статический `SamplerComparisonState`,
`COMPARISON_MIN_MAG_LINEAR_MIP_POINT`, `LESS_EQUAL`, `BorderColor = OPAQUE_WHITE`
(за пределами карты всё освещено). В шейдере 3×3 `SampleCmpLevelZero`; каждая
выборка уже билинейна, так что фактически ядро 4×4.

## Вопросы

**Почему описанная сфера, а не AABB?** У AABB размер зависит от ориентации
под-фрустума: при вращении камеры каскад то растёт, то сжимается, разрешение
скачет и тени «кипят». Радиус сферы от поворота не зависит.

**Зачем `DepthBiasClamp`?** Слайд 20: на полигоне под острым углом к свету
формула наклона даёт огромное смещение, и тень отрывается от объекта
(peter-panning). Клэмп это ограничивает.

**Почему усредняются сравнения, а не глубины?** Усреднить глубины и сравнить один
раз — значит просто сдвинуть жёсткую границу. Размытие даёт именно усреднение
бинарных результатов (слайд 39).

**Почему глубина пикселя берётся в пространстве камеры?** Потому что границы
каскадов хранятся там же. Значение [0..1] из буфера глубины нелинейно и с ними
несравнимо (слайд 31).

**Почему тени только у направленного света?** Каскады строятся под ортогональную
проекцию. Точечному нужна кубическая карта (6 граней), прожектору — своя
перспективная (слайд 13).

**Цена?** 4 среза × 2048² × 4 байта = **64 МБ** только на карты теней, плюс
отдельный проход отрисовки всей геометрии на каждый каскад.

**Показать:** `H` — тени, `M` — подкрасить каскады, `K`/`L` — смещение,
`U`/`I` — λ (0 — равномерное, 1 — логарифмическое; на 0 видно, как портится
ближний каскад).

**Не закрыто:** альфа-тест в проходе теней (листва отбрасывает сплошные
прямоугольники), смешивание на границе каскадов, PCSS/VSM, SSAO (слайды 41–48).

# Лаба 6 — Система частиц

**Задание (лекция 07, слайд 77):** сделать систему частиц для непрозрачных частиц;
два `StructuredBuffer` — один Append, второй Consume; геометрический шейдер для
развёртывания точек в билборды; обновление позиций **обязательно** в compute-шейдере;
сортировка на GPU — на дополнительный балл.

## Решение

- `MaxParticles = 65536`, частица 64 байта → буфер 4 МиБ, их два = 8 МиБ.
- **Два буфера с ролями «приёмник/источник», меняются местами каждый кадр.**
  UAV-счётчики живут в **отдельных ресурсах** `m_counters[0..1]` (по 256 байт):
  `CounterOffsetInBytes` должен быть кратен 4096, поэтому смещение 0 и отдельный
  ресурс.
- Куча: 2 набора × 5 дескрипторов = `u0` append, `u1` consume, `u2` снимок,
  `u3` счётчик приёмника, `t0` SRV для рендера.
- Два ядра, `[numthreads(64,1,1)]`: `UpdateCS` диспатчится на весь пул
  (1024 группы), `EmitCS` — `(EmitCount + 63)/64` групп.
- ГПСЧ — целочисленный хеш triple32, зерно из `SV_DispatchThreadID` и `FrameIndex`.
- Отрисовка: `POINTLIST`, ни VB ни IB, `ExecuteIndirect` с `CommandSignature`
  типа `_TYPE_DRAW`. GS разворачивает точку в 4 вершины (`[maxvertexcount(4)]`).
- Частицы пишут в **тот же G-Buffer** — значит освещаются общим световым проходом.

## Ключевой код

```hlsl
// UpdateCS: интегрирование Эйлера (слайд 8), смерть = просто не аппендить
uint aliveCount = gCountSnapshot.Load(0);
if (dtid.x >= aliveCount) return;

p.Age += gDeltaTime;
if (p.Age >= p.Lifetime) return;          // частица умерла (слайд 19)

float3 acceleration = gGravity - p.Velocity * gDrag;
p.Velocity += acceleration * gDeltaTime;
p.Position += p.Velocity   * gDeltaTime;

gDstParticles.Append(p);
```

```cpp

cmd->CopyBufferRegion(m_drawArgs.Get(), 0, m_zeroBuffer.Get(), 16, sizeof(D3D12_DRAW_ARGUMENTS));
cmd->CopyBufferRegion(m_drawArgs.Get(), 0, m_counters[dst].Get(), 0, sizeof(UINT));
```


`CameraRight`/`CameraUp` — это строки матрицы вида, то есть оси камеры в мировом

## Вопросы

**Зачем `countSnapshot`, почему нельзя прочитать живой счётчик?** `UpdateCS` должен
знать, сколько частиц было живо, чтобы лишние потоки вышли **до** вызова
`Consume()` — иначе счётчик уйдёт в underflow. Но в этот момент живой счётчик
дёргают `Consume()` соседних потоков, читать его нельзя. Поэтому в конце кадра
счётчик копируется в отдельный буфер, и следующий кадр читает снимок. Это главный
вопрос по этой лабе.

**Почему CPU не знает число живых частиц?** Оно есть только на GPU. Читать обратно
означало бы синхронизацию. Вместо этого счётчик копируется прямо в
`D3D12_DRAW_ARGUMENTS` и используется `ExecuteIndirect` — ровно как советует
слайд 18.

**Где хранится список свободных слотов?** Его нет и не нужно: Append/Consume
и есть пул. Умершая частица просто не аппендится в приёмник.

**Почему нет сортировки?** Частицы непрозрачные, блендинг выключен, прозрачность
сделана альфа-тестом `clip()` — порядок разрешает буфер глубины. Сортировка нужна
для альфа-смешения (слайд 45); битоническая сортировка — доп. балл, не делалась.

**Как круг получается из квадрата?** `clip(1 - dot(Corner, Corner))` — отбрасываются
пиксели вне единичного радиуса в локальных координатах билборда.

**Зачем «сферическая» нормаль?** Чтобы отложенный свет давал частице объём, а не
плоскую карточку: нормаль собирается из осей билборда и `sqrt(1 − r²)` по оси
взгляда.

**Интегрирование?** Явный (полунеявный) Эйлер: сначала скорость, потом позиция
по новой скорости. Силы — только гравитация и линейное сопротивление `−v·Drag`.

**Почему `dt` клампится?** `min(dt, 0.05)` — при рывке (20 FPS и хуже) частицы
иначе телепортируются на пол-сцены за кадр.

**Показать:** `J` — эмиссия вкл/выкл (видно, как живые частицы доживают срок),
`R` — сброс, `Z`/`X` — частота эмиссии (по умолчанию 12000 частиц/с).

**Не закрыто:** сортировка на GPU, soft particles (слайды 75–76), коллизии по
буферу глубины (73–74), тени от частиц (40–43), tiled rendering (58–69),
текстура частицы (только процедурный диск), velocity-aligned билборды.

# Лаба 7 — Пост-эффекты

Лекции 08.1 (гамма) и 08.2 (постобработка). **Слайда с домашним заданием нет**,
поэтому реализован весь материал обеих частей.

## Цепочка

```
Light pass ──> HDR (R16G16B16A16_FLOAT, линейное пространство)
                 ├─> Bright pass ──> Bloom[0] (1/4 разрешения)
                 │     Blur H    ──> Bloom[1]
                 │     Blur V    ──> Bloom[0]
                 └─> Composite ──> бэк-буфер (RTV формата _SRGB)
```

## Гамма-коррекция — три места

1. **Финальный RTV.** Swap chain остаётся `R8G8B8A8_UNORM` (flip-модель
   не принимает `_SRGB` для самой цепочки), но RTV на те же буферы создаётся
   с `R8G8B8A8_UNORM_SRGB`. Шейдер отдаёт линейный цвет, кодирует блок вывода
   (слайд 43).
2. **Диффузные текстуры** — SRV с `_SRGB`-вариантом формата. Карты нормалей,
   высот и альфа-маски цветом не являются, им гамма противопоказана (слайд 42).
3. **Альбедо в G-Buffer** — `R8G8B8A8_UNORM_SRGB`: 8 бит в линейном пространстве
   дают полосы в тенях (слайд 51).

## HDR и тональное отображение

Промежуточный буфер `R16G16B16A16_FLOAT`: свет накапливается аддитивно и уходит
за единицу, в 8-битном UNORM всё выше 1.0 обрезалось бы (saturation, слайд 5).

| Режим (клавиша 5) | Формула |
|---|---|
| выкл | `saturate(hdr · exposure)` — видно, как выгорают света |
| Рейнхард | `hdr / (hdr + 1)` (слайд 6) |
| экспозиционный | `1 − exp(−hdr · exposure)` (слайд 7) |

## Bloom

Bright pass с **мягким** порогом: жёсткая отсечка заставляет свечение мерцать,
когда пиксели пересекают порог от кадра к кадру. Размытие **сепарабельное**
(слайд 18): ядро N×N раскладывается в два прохода, N·N выборок → 2·N. Буферы
в четверть разрешения — уменьшение само по себе размывает, поэтому ядро короткое
(7 отсчётов). Свечение добавляется **до** тонального отображения: это утечка
света внутри камеры, значит должно пройти ту же кривую отклика.

## Дизеринг (слайды 53–60)

Матрица Байера 4×4, порог ±0.5 младшего бита. Тонкость: квантование происходит
**в закодированном пространстве**, поэтому шум добавляется после перевода в sRGB
и возвращается обратно — аппаратный `_SRGB`-кодировщик повторит преобразование
точно так же.

```hlsl
float3 encoded = LinearToSrgb(linearColor);
encoded += threshold / 255.0f;
return SrgbToLinear(encoded);
```

## Вопросы

**Что такое гамма и зачем она?** Исторически — нелинейный отклик ЭЛТ-мониторов
(слайды 2–4). Сейчас — схема сжатия: глаз различает больше оттенков в тёмной части,
и гамма-кодирование отдаёт им больше кодов (слайды 22–25).

**Что будет, если не корректировать?** Двойная гамма: текстуры, уже
гамма-закодированные, используются как линейные, результат темнее и с уходом
оттенков. Признаки — мелкие текстуры и мипы темнее, чем должны (слайд 34).

**Почему сепарабельное размытие быстрее?** Двумерное гауссово ядро — внешнее
произведение двух одномерных. Для ядра 7×7: 49 выборок против 2×7 = 14.

**Почему bloom до тонального отображения, а виньетка после?** Bloom — физический
процесс в оптике камеры, он происходит с линейным светом до отклика сенсора.
Виньетка и хроматическая аберрация — тоже дефекты объектива, но их проще применять
к готовому LDR-изображению без заметной разницы.

**Почему отладочные виды идут мимо цепочки?** `SetPassthrough` включается при
`m_debugMode != 0`, иначе нормали и глубина исказились бы тональным отображением.

**Показать:** `5` — три режима тонмаппинга по кругу, `Q`/`E` — экспозиция (видно
выгорание в режиме «выкл»), `4` — bloom, `6` — дизеринг, `7` — виньетка,
`8`/`9` — порог свечения.

**Не закрыто:** адаптация зрачка (слайды 9–11) — нужна средняя яркость через мипы
или compute-редукцию и хранение между кадрами; lens flares, DoF, SSR, god rays —
обзорный материал; цветокоррекция через LUT-куб (слайд 33).

# Лаба 8 — PBR

Лекция 09. **Слайда с домашним заданием нет**, реализован материал лекции:
Cook-Torrance + metallic workflow, окружение по схеме IBL.

## Что поменялось

Третий таргет G-Buffer: было `rgb = Ks, a = Ns/255`, стало
`r = metallic, g = roughness, b = AO`. Формат остался `_UNORM`, **не** `_UNORM_SRGB` —
это параметры BRDF, а не цвет, гамма исказила бы их смысл.

## Откуда metallic и roughness

В Wavefront их нет. Шероховатость выводится из экспоненты Фонга: `alpha = sqrt(2/(Ns+2))`,
а по слайду 23 `alpha = Roughness²`, значит

```
Roughness = (2 / (Ns + 2))^(1/4),   зажата в [0.05, 1.0]
```

Нижний зажим обязателен: при `roughness → 0` знаменатель GGX уходит в ноль и
появляются одиночные пересвеченные пиксели — «светлячки».

Металличность — не градиент, а признак (слайды 33–34: у диэлектриков F0 ≤ 0.17,
у проводников от 0.5 и подкрашена). В Sponza металлы опознаются по имени материала:
`chain`, `flagpole`, `metal`.

## BRDF

**D — Trowbridge-Reitz GGX** (слайды 23–24): доля микрофасетов, чья нормаль смотрит
вдоль halfway-вектора H.

```hlsl
float a = roughness * roughness;   float a2 = a * a;
float d = NdotH * NdotH * (a2 - 1.0f) + 1.0f;
return a2 / max(PI * d * d, 1e-7f);
```

**G — Schlick-GGX по методу Смита** (слайды 25–27): самозатенение. Смит считает
обзор (obstruction) и свет (shadowing) независимо и перемножает. `k = (r+1)²/8`
для прямого света; для IBL на том же слайде другая формула — `r²/2`.

**F — Френель-Шлик** (слайды 28–29): доля отражённого света, растущая к скользящим
углам.

```hlsl
float3 F0 = lerp(float3(0.04, 0.04, 0.04), albedo, metallic);   // слайд 33
```

**Сборка** (слайд 35):

```hlsl
float3 specular = (D * G * F) / max(4.0f * NdotV * NdotL, 1e-4f);
float3 kD = (1.0f - F) * (1.0f - metallic);
float3 Lo = (kD * albedo / PI + specular) * radiance * NdotL;
```

## Окружение

Полный IBL требует трёх запечённых текстур. Их нет, поэтому окружение считается
аналитически, но по структуре слайда 80:

| Слайд 80 | Здесь |
|---|---|
| `irradianceMap.Sample(N)` | `SkyIrradiance(N)` — градиент неба, свёрнутый по полусфере |
| `prefilterMap.SampleLevel(R, rough·MAX_LOD)` | `PrefilteredSky(R, rough)` — тот же градиент, размытый по шероховатости |
| `brdfLUT.Sample(NdotV, rough)` | `EnvBRDFApprox` — аналитическая аппроксимация Кариса |

Френель здесь берётся в roughness-варианте (слайд 55): у окружающего света нет
halfway-вектора, слайд 54 подставляет N, но тогда эффект переоценивается на
шершавых поверхностях.

## Вопросы

**Почему нигде не вычисляется `kS`?** Слайд 35 прямо об этом: `F` **и есть** доля
отражённого света, то есть `kS`. Зеркальная часть BRDF содержит его неявно.
Домножить `specular` на `kS` — двойной учёт. Любимый вопрос преподавателей.

**Почему `(1 − metallic)` у диффузной части?** Слайд 9: у металла вся преломлённая
часть поглощается, диффузного цвета нет вообще. Без множителя металл выглядел бы
крашеной пластмассой.

**Зачем делить на π?** Ламбертова диффузия — `c/π` (слайд 20). Без деления
поверхность излучает больше, чем получает, — нарушение сохранения энергии.

**Почему у шероховатой поверхности блик тусклее?** Слайд 6: та же энергия
размазывается по большему телесному углу. Если бы интенсивность была та же,
шероховатая поверхность излучала бы больше.

**Чем PBR лучше Фонга?** Слайд 2: материал выглядит правдоподобно **вне
зависимости от условий освещения**. У Фонга `Ks` и `Ns` подбираются под конкретную
сцену и разваливаются при смене света.

**Почему поле объектов стало разноцветной таблицей?** `Center.w` и `Extent.w` были
пустым выравниванием в 48-байтной записи экземпляра — туда положены metallic
и roughness по нормированной позиции коробки. Размер записи и input layout
не изменились.

# Часть 9. Вопросы «не по лабе», которые задают всем

**Сколько памяти ест ваш кадр?** G-Buffer 1920×1080: альбедо 4 + нормали 8 +
материал 4 = 16 байт/пиксель ≈ 33 МБ, плюс глубина 4 байта ≈ 8 МБ, плюс HDR-буфер
8 байт ≈ 16 МБ, плюс два буфера свечения в 1/4 разрешения, плюс карты теней 64 МБ,
плюс два буфера частиц 8 МБ.

**Где у вас барьеры и почему именно там?** После геометрического прохода G-Buffer
переводится `RENDER_TARGET → PIXEL_SHADER_RESOURCE`, depth — `DEPTH_WRITE →
PIXEL_SHADER_RESOURCE`; обратно в начале следующего кадра. У частиц — UAV-барьеры
между `UpdateCS` и `EmitCS` (пишут в один буфер), затем переход буфера аргументов
в `INDIRECT_ARGUMENT`.

**Почему у вас несколько root signature?** Разные проходы читают разные ресурсы.
Одна большая сигнатура заставила бы каждый проход тащить неиспользуемые параметры,
а слайд 34 лекции 05 советует обратное — минимальную сигнатуру с флагами
`DENY_*_SHADER_ROOT_ACCESS`.

**Где у вас транспонирование матриц и почему не везде?** В константные буферы
матрицы кладутся транспонированными — HLSL читает cbuffer по столбцам. А при
ручном разборе элементов (извлечение плоскостей пирамиды, осей камеры)
транспонировать **нельзя** — там нужен исходный row-vector-вид DirectXMath.

**Что бы вы улучшили в первую очередь?** Убрал бы `FlushCommandQueue()` каждый кадр
и сделал frame resources — сейчас CPU и GPU работают строго по очереди.
